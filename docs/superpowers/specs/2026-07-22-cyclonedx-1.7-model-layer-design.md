# Design: CycloneDX 1.7 support + model (IR) layer

- **Date:** 2026-07-22
- **Issue:** [#175 — Add CycloneDX 1.7 support via cyclonedx-go v0.11.0](https://github.com/OmniTrustILM/cbom-lens/issues/175)
- **Status:** superseded for Ticket 2 by
  [2026-07-28-cyclonedx-1.7-emit17-design.md](2026-07-28-cyclonedx-1.7-emit17-design.md);
  Tickets 0–1 shipped (PR #177). Tasks 1.5–1.9 (converter migration) were dropped
  as a prerequisite: Builder-level extraction of the crypto relationships gives the
  1.7 emitter everything it needs with no `internal/cdxprops` changes, so converter
  migration is now independent cleanup.

## Problem

Issue #175 asks cbom-lens to emit CycloneDX 1.7 (crypto-registry semantics), validate
against the 1.7 schema, and consider defaulting to it. Investigation shows this is not a
clean dependency bump: business logic is coupled to the CycloneDX wire format, and 1.7
deprecates/renames several fields cbom-lens writes.

### Fields cbom-lens writes that change in 1.7

Verified against `bom-1.7.schema.json` and a v0.10.0↔v0.11.0 `cyclonedx-go` struct diff.
`cyclonedx-go` v0.11.0 keeps deprecated fields (no exported symbol removed — the bump is
API-safe), so a naive bump compiles but keeps emitting deprecated mechanics.

| Field written | Location(s) | 1.7 change | 1.7 target |
|---|---|---|---|
| `CertificateProperties.SignatureAlgorithmRef` | `x509.go:102` | deprecated | `relatedCryptographicAssets` (`type:"algorithm"`) |
| `CertificateProperties.SubjectPublicKeyRef` | `x509.go:103` | deprecated | `relatedCryptographicAssets` (`type:"publicKey"`) |
| `CertificateProperties.CertificateExtension` | `x509.go:151` | renamed | `CertificateFileExtension` |
| `AlgorithmProperties.Curve` | `nmap.go:25,29,33,37,285`, `signature_algorithm.go:243` | renamed | `EllipticCurve` |
| `RelatedCryptoMaterialProperties.AlgorithmRef` | `pem.go:161`, `private_key.go:34`, `public_key.go:68` | deprecated | `relatedCryptographicAssets` |
| `ProtocolProperties.CryptoRefArray` | `nmap.go:270` | deprecated | `relatedCryptographicAssets` |

Two kinds of change:
- **Field renames** (`CertificateExtension`→`CertificateFileExtension`, `Curve`→`EllipticCurve`):
  pure per-emitter field mapping, no relationship modeling needed.
- **Ref moves** (`SignatureAlgorithmRef`, `SubjectPublicKeyRef`, `AlgorithmRef`,
  `CryptoRefArray` → `relatedCryptographicAssets`): these are *crypto relationships*
  currently written as version-specific wire fields; they need to move into the model layer.

### Format coupling in business logic

The business layer both **writes** version-specific refs and **reads them back**:
- `nmap.go:104-107` parses `SubjectPublicKeyRef` (an algorithm bom-ref today) to derive
  the TLS auth key size — a business rule depending on serialization.
- Other read-backs of cdx fields exist (`cdxprops.go:65` reads
  `RelatedCryptoMaterialProperties.Type`; `cdxprops.go:159` reads a component `BOMRef`
  to derive a PEM private-key id). These are internal read-backs, not version-sensitive,
  but confirm the pattern.

## Goals

- Emit CycloneDX 1.7 using 1.7 crypto-registry semantics; validate against the 1.7 schema.
- Keep CycloneDX 1.6 output available. **Default stays 1.6; 1.7 is opt-in** (see Decisions).
- Isolate two concerns behind a boundary: business logic that decides *what* crypto assets
  and relationships exist, vs. the format concern that decides *how* they serialize per
  spec version.

## Non-goals

- Re-modeling every crypto asset into a fully cdx-independent type system (see
  "Alternatives"). The IR is deliberately **targeted**.
- Changing scanner-native models (`model.CertHit`, `model.Leaks`, `model.Nmap`,
  `model.PEMBundle`).
- Adopting unrelated 1.7 features (patents, provenance/citations, TLP, license details).
- Fixing the `SubjectPublicKeyRef`-points-at-algorithm quirk in 1.6 output (preserved for
  byte-compat; see Open questions).

## Decisions (post-review)

1. **Default version stays 1.6; 1.7 is opt-in.** Defaulting to 1.7 would move
   `signatureAlgorithmRef`/`subjectPublicKeyRef` into `relatedCryptographicAssets` and
   could silently break the CZERTAINLY consumer that ingests this output. The default flip
   is a coordinated cross-repo change, deferred until 1.7 ingestion is verified downstream.
2. **Determinism is a prerequisite pre-step (Ticket 0).** The current `BOM()` ranges Go
   maps (`builder.go:112,120`) → top-level `Components`/`Dependencies` arrays are ordered
   randomly *every run*, and `serialNumber`/`timestamp` are non-deterministic
   (`builder.go:134,137`). A byte-identical golden gate is therefore impossible today.
   We first make output deterministic (sort arrays; injectable serial/timestamp), accept
   the one-time byte reordering of 1.6 output (semantically identical), and capture the
   golden from *that*. All subsequent refactor work is gated against the deterministic golden.
3. **Targeted IR**, not a full native re-model (blast radius: ~15 `cdxprops` files).

## Architecture

Four layers (IR is new); ref-rewrite and dedup live at defined layers:

```
scanners → [scanner models]  (internal/model)                              unchanged
   │
   ▼  Converter (internal/cdxprops)              business logic, version-neutral
[ lens IR: Assets + Relationships + KeyInfo + evidence ]
   │
   ▼  bom.Builder                                dedup + evidence-merge + ref canonicalization
[ BOMModel: deduped assets, relationships, metadata ]
   │
   ▼  Emitter (per cdx.SpecVersion)              format concern
cdx.BOM   (emit16 | emit17)
```

- `Converter` produces IR; it no longer writes version-specific ref/rename fields.
- `Builder` dedupes assets by ref, merges evidence occurrences, and **canonicalizes refs**
  (replacing today's reflection-based `safeRefs`, see below), producing a `BOMModel`.
- Each `Emitter` renders `BOMModel` → `cdx.BOM` for one spec version.

## The model layer (IR) — targeted

Proposed package: **`internal/model/cbom`** (sibling of the existing scanner/config models
under `internal/model`; `internal/bom` remains emission).

```go
// AssetRef is the canonical identity. Assets and relationships reference it; emitters
// translate it into wire bom-refs exactly once. Prevents Asset.Ref / Component.BOMRef drift.
type AssetRef string

// Asset owns the cdx payload plus lens-only metadata (no parallel map keyed by ref).
type Asset struct {
    Ref       AssetRef      // canonical; emitter sets Component.BOMRef from this
    Component cdx.Component  // payload (reused struct; relationship wire fields NOT set here)
    Key       *KeyMeta       // optional read-back metadata, co-located with its asset
}

type KeyMeta struct {
    // Size is a STRING: RSA→bits ("2048"); EC→curve name ("secp256r1").
    // (publicKeySizeFromPkeyRef, nmap.go:120-134, returns either — an int would drop EC.)
    Size string
}

type Relationship struct {
    From AssetRef
    To   AssetRef
    Kind RelationshipKind
}

type RelationshipKind string
const (
    // Crypto-asset relationships. 1.6 → specific deprecated ref fields;
    // 1.7 → relatedCryptographicAssets with the mapped `type`.
    RelSignatureAlgorithm RelationshipKind = "signature-algorithm" // → 1.7 type "algorithm"
    RelSubjectPublicKey   RelationshipKind = "subject-public-key"  // → 1.7 type "publicKey"
    RelMaterialAlgorithm  RelationshipKind = "material-algorithm"  // key/material → algorithm
    RelProtocolCrypto     RelationshipKind = "protocol-crypto"     // protocol → algorithm(s)
    // Generic dependency-graph edge (dependsOn), unchanged across versions.
    RelDependsOn RelationshipKind = "depends-on"
)

type Detection struct {
    Source   string
    Type     DetectionType
    Location string
    Assets   []Asset
    Services []cdx.Service
    Rels     []Relationship
}
```

Business-layer changes:
- `x509.go` records `RelSignatureAlgorithm` / `RelSubjectPublicKey` / `RelDependsOn` edges
  instead of setting the deprecated cert ref fields; the file extension value moves to IR.
- `pem.go` / `private_key.go` / `public_key.go` record `RelMaterialAlgorithm` instead of
  `RelatedCryptoMaterialProperties.AlgorithmRef`.
- `nmap.go` records `RelProtocolCrypto` instead of `ProtocolProperties.CryptoRefArray`, and
  reads key size from the cert `Asset.Key` (IR) instead of parsing `SubjectPublicKeyRef`.
  The nested-`CertHit` path (`nmap.go:82-110`) must propagate `Asset.Key` out of the nested
  cert detection.
- `Curve` is recorded into the IR's algorithm asset in a version-neutral way; emitters write
  `Curve` (1.6) or `EllipticCurve` (1.7).

## Ref canonicalization (replaces reflection `safeRefs`)

Today `safeRefs`/`replaceBOMReferences` (`builder.go:237-333`) rewrite refs by walking
`cdx.Component` with reflection, matching fields of type `cdx.BOMReference`. This breaks in
the new design:
- IR `Relationship.From/To` and `AssetRef` are plain strings → reflection would skip them.
- 1.7's `RelatedCryptographicAsset.Ref` is a plain `string` (not `BOMReference`) → reflection
  would **not** rewrite emit17 refs, producing dangling references.

Fix: `Builder` owns an explicit `AssetRef → wire-ref` map and translates **all** refs
through it — asset refs, relationship endpoints, and dependsOn edges — before/at emit time.
Emitters render relationships into wire fields and set every produced ref from the same map.
No reliance on struct-field type matching.

## Emitter interface

```go
type Emitter interface {
    SpecVersion() cdx.SpecVersion
    Emit(ctx context.Context, m BOMModel) cdx.BOM   // BOMModel is already deduped/canonical
}
```

- **emit16** (`internal/bom/emit16.go`): relationships → `SignatureAlgorithmRef` +
  `SubjectPublicKeyRef` + `AlgorithmRef` + `CryptoRefArray` + `dependsOn`; `CertificateExtension`;
  `Curve`. **Must reproduce the deterministic (Ticket 0) 1.6 output byte-for-byte.**
- **emit17** (`internal/bom/emit17.go`): relationships →
  `CertificateProperties.RelatedCryptographicAssets` /
  `RelatedCryptoMaterialProperties.RelatedCryptographicAssets` /
  `ProtocolProperties.RelatedCryptographicAssets`
  (`[]RelatedCryptographicAsset{Type, Ref}`); `CertificateFileExtension`; `EllipticCurve`;
  keep `dependsOn`. `provides` is **not** used (schema semantics = "implements a spec", not
  cert/material composition — verified against `dependency.provides`).

### `relatedCryptographicAsset.type` vocabulary

The 1.7 schema defines `relatedCryptographicAsset.type` as a free **string with no enum**
(examples: `publicKey`, `privateKey`, `algorithm`). So the schema will **not** catch wrong
values. Mapping:
- `RelSignatureAlgorithm` → `type:"algorithm"`
- `RelSubjectPublicKey` → `type:"publicKey"`
- `RelMaterialAlgorithm` → `type:"algorithm"`
- `RelProtocolCrypto` → `type:"algorithm"`

Define these as named constants and assert emitted `type` values in a golden test (schema
validation alone is insufficient).

## Dedup & ordering semantics (IR)

- **Assets**: deduped by `AssetRef` (as today by `BOMRef`); evidence occurrences merged +
  sorted (as `addEvidenceLocation` does today).
- **Relationships**: deduped by `(From, To, Kind)`. The current one-to-many cert edge
  `sigAlg → {pubKeyAlg, hashAlg}` (`x509.go:121-129`) splits into per-edge `RelDependsOn`;
  emit16 must regroup them into a single `dependsOn` array **preserving the original element
  order** (pubKeyAlg before hashAlg) to stay byte-identical.
- **Output arrays** sorted deterministically (Ticket 0): components by wire bom-ref,
  dependencies by ref.

## Schema / config / version-selection surfaces

Add `internal/bom/schemas/bom-1.7.schema.json`; make version drive output instead of the
hardcoded 1.6. Surfaces to change (from review):
- `internal/model/config.go:162` — spec-version config field (default stays `"1.6"`).
- `internal/bom/builder.go:43-48` — version→SpecVersion map; add `1.7`.
- `internal/bom/builder.go:130-133` — stop hardcoding `JSONSchema`/`SpecVersion`; derive.
- `internal/bom/validator.go:14-19` — embed + map the 1.7 schema.
- `internal/service/client.go:19` — upload content-type currently hardcodes 1.6.
- `internal/dscvr/const.go:55` — doc string says default 1.6 (stays correct).

## Ticket split (sequencing)

**Ticket 0 — deterministic output (prerequisite).**
Sort top-level `Components`/`Dependencies`; make `serialNumber`/`timestamp` injectable.
One-time byte reordering of 1.6 output (semantically identical). Capture the golden.
Separate commit so it is cleanly revertable and so the golden diff is reviewable in isolation.

**Ticket 1 — model (IR) layer refactor. Zero behavior change vs Ticket 0 golden.**
- Add `internal/model/cbom` IR (`AssetRef`, `Asset`, `KeyMeta`, `Relationship`, `Detection`).
- `Converter` produces IR; `Builder` produces `BOMModel` with explicit ref canonicalization
  (replacing reflection `safeRefs`) + dedup/evidence-merge; add `Emitter` + emit16.
- Move **all** version-sensitive writes/read-backs into IR: cert refs, material `AlgorithmRef`,
  protocol `CryptoRefArray`, `Curve`, and the nmap key-size read-back.
- No cyclonedx-go bump. **Output stays deterministic 1.6, byte-identical to Ticket 0 golden.**

**Ticket 2 — CycloneDX 1.7 (#175).**
- Bump `cyclonedx-go` → v0.11.0 (API-safe).
- Add `bom-1.7.schema.json` + emit17 + version config; **1.7 opt-in, default 1.6**.
- Emit17 covers every remap in the field table + relationship rendering.

## Testing

- **Ticket 0:** capture deterministic golden(s) for the existing corpus; assert stable
  across repeated runs (no map-order flakiness).
- **Ticket 1 safety net:** golden test — corpus emits *byte-identical* 1.6 JSON before/after
  the refactor (against the Ticket 0 golden). Add a test asserting `Asset.Key` (key size) is
  populated for **every** cert-with-public-key path the old wire-parse covered (RSA bits and
  EC curve), guarding the read-back migration.
- **Ticket 2:**
  - Validate emitted 1.7 against `bom-1.7.schema.json` (reuse `internal/bom/validator.go`).
  - Golden 1.7 fixtures; **assert `relatedCryptographicAssets[].type` values** (schema won't).
  - Assert deprecated fields (`signatureAlgorithmRef`, `subjectPublicKeyRef`, `algorithmRef`,
    `cryptoRefArray`, `curve`, `certificateExtension`) absent from 1.7 output.
  - Assert nmap key-size derivation still correct (now via IR) in both RSA and EC cases.
  - 1.6 output still validates and is unchanged.

## Open questions

- **`SubjectPublicKeyRef` semantic quirk:** today it points at the *algorithm* component,
  not the public-key component (`x509.go:103`). Preserved as-is for 1.6 byte-compat. For 1.7,
  decide whether `RelSubjectPublicKey` should reference the public-key asset (correct) or keep
  pointing at the algorithm (bug-compatible). Recommend fixing in 1.7 only, documented as a
  deliberate divergence.

## Alternatives considered

- **Full native IR** — re-model every crypto asset independent of cdx. Cleanest separation
  but rewrites all ~15 `cdxprops` files; large and riskier. Rejected for now; the targeted IR
  can grow into this later.
- **Naive dependency bump only** — compiles and may validate, but keeps deprecated mechanics
  and leaves the coupling in place. Rejected.
- **Single combined ticket** — mixes provably-no-op refactor with new format, losing the
  byte-identical bisect boundary. Rejected.
- **Order-insensitive (normalized) diff instead of Ticket 0 determinism** — avoids changing
  1.6 output bytes, but yields a weaker gate. Rejected in favor of deterministic output,
  which is independently valuable (reproducible CBOMs).
